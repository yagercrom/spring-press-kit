# 교육의봄 보도자료 작성

교육의봄 보도자료는 서식이 고정돼 있고, 그 서식에는 이유가 있다. 기자는 메일 제목의 `★태그`로 자료 성격을 즉시 판단하고, 헤드라인의 수치를 그대로 기사 리드로 옮기며, 박스 안 조사 개요로 신뢰도를 검증한다. 서식을 흐트러뜨리면 그 세 가지가 전부 느려진다.

이 스킬은 두 가지를 한다. **무엇을 어떤 순서로 쓸지**(아래 + `references/`)와 **기관 서식 그대로의 HWPX 생성**(`tools/build_press_release.py`).

## 0단계: 유형을 먼저 확정한다

유형에 따라 본문 구조·기호·문체가 갈리므로, 쓰기 시작하기 전에 반드시 정한다.

| 유형 | ★태그 | 성격 |
|---|---|---|
| **A. 조사·설문 발표형** | `[★N차 분석]` `[★분석보도]` `[★회견보도]` | 자체 설문·실태조사 결과를 수치 중심으로 공표 |
| **B. 회견·성명 보도형** | `[★회견보도]` | 기자회견·공동성명 등 행사·입장 발표 |
| **C. 이슈 심층 분석형** | `[★심층보도]` | 외부 사건·현상을 분석·해석 |

한 건이 두 성격을 겸할 수 있다. 실태조사를 기자회견으로 발표하면 태그는 `[★회견보도]`, 본문은 A형 구조를 쓴다.

유형이 정해지면 **해당 레퍼런스를 읽고 그 구조를 따를 것.** 유형별로 본문 블록이 다르다.

| 유형 | 읽을 것 |
|---|---|
| A | `references/type-a-survey.md` |
| B | `references/type-b-statement.md` |
| C | `references/type-c-analysis.md` |

## 문체: 자리에 따라 어미가 갈린다

이것이 교육의봄 보도자료에서 가장 자주 틀리는 지점이다. **한 문서 안에 두 어미 체계가 공존하며, 자리마다 정해져 있다.**

| 자리 | 어미 | 예 |
|---|---|---|
| `❏` 개요·배경 | **명사형** | `~수집·분석하였음`, `~높여왔음` |
| 박스 안 결과 요약 | **명사형** | `~나타남`, `~있었음` |
| `■ 결과N` 제목 | **명사형** | `~확립된 것으로 나타남` |
| 결과 본문 해설 | **존댓말** | `~나타났습니다`, `~확인되었습니다`, `~잡았습니다` |
| `■` 기관 입장 | **명사형** | `~진전임`, `~분명히 하는 것임`, `~제안함` |
| `①` 제언 | **명사형** | `~요구해야 함`, `~검토할 필요가 있음` |
| 맨 마지막 클로징 | **존댓말** | `~벗어날 수 없게 됩니다`, `~지속해 나갈 것입니다` |

즉 **골격(개요·요약·입장·제언)은 명사형, 읽히는 서술(결과 해설·클로징)은 존댓말**이다. 개요를 존댓말로 쓰거나 결과 해설을 명사형으로 쓰면 바로 이질적으로 읽힌다.

그 외 공통 표현:
- 해석: `이는 ~임을 시사합니다`, `이를 통해 ~을 확인하였습니다`
- 강조 도입: `눈에 띄는 부분은 ~입니다`
- 제언: `~방향으로 추진되어야 합니다`, `~기대합니다`

## 기호 체계

실제 발행 문서 기준이다. 지침 문서에는 `□`로 적혀 있으나 발행본은 `■`를 쓴다.

| 기호 | 자리 |
|---|---|
| `❏` | 개요·배경·요약 도입 문단 |
| `■` | 본문 결과 제목, 기관 입장, 클로징 |
| `-` | 부제 보조 bullet, 박스 안 항목 |
| `①②③④⑤` | 시사점·제언 번호 |
| `※` | 표 주석, 보충 설명 |
| `[표 N]` | 표 캡션 (표 **위**에 배치) |

## 수치 표기

| 대상 | 형식 |
|---|---|
| 비율 | `70.4%` — 소수점 1자리 |
| 개수 병기 | `96.3%(26개)` — 비율 먼저, 괄호에 실수 |
| 집단 비교 | `사무직 70.4%·기술직 66.7%` — 가운뎃점으로 연결 |
| 차이값 | `38.1%p` |
| 금액 | `월 30만원` — 기간 단위 명시 |
| 발행일 | `2026. 8.  .` — 일자는 비워 두고 발송 시 기입 |

## 작성 순서

1. **유형 확정** → ★태그 결정
2. **자료 탐독** — 설문 원데이터, 회견문, 외부 기사·통계 등 제공된 자료를 먼저 다 읽는다. 수치를 추정하거나 반올림해 만들어 내지 말 것. 근거 없는 수치는 보도자료에서 가장 치명적인 실수다.
3. **유형별 레퍼런스 읽기**
4. **plan JSON 작성** — `references/plan-schema.md` 참조, `examples/plan-type-a.json` 이 동작하는 예시
5. **HWPX 생성** (아래)
6. **검증** — 생성 후 반드시 확인 (아래)

## HWPX 생성

```bash
python "<SKILL_DIR>/tools/build_press_release.py" --plan plan.json --output 보도자료.hwpx
```

생성기는 `assets/press-release-reference.hwpx`(실제 발행본)를 **스타일 공급원**으로 쓴다. 모든 문단은 그 문서의 문단을 복제해 텍스트만 바꾼 것이므로 글꼴·크기·들여쓰기·박스 테두리가 원본과 같다. 새로 조립하지 않는 이유는 이 서식이 `header.xml`의 스타일 정의에 묶여 있어서, 정의 없이 문단만 만들면 전혀 다르게 보이기 때문이다.

`tools/`에 있는 이유: hwpx 스킬이 프리미티브를 `scripts` 라는 이름의 패키지로 노출하므로, 여기에 `scripts/`를 두면 그것을 가려서 임포트가 깨진다.

### 줄 기하 정보 — 건드리지 말 것

생성기는 문단마다 `<hp:linesegarray>`(줄 시작 위치·세로 좌표)를 **새 텍스트 기준으로 다시 계산**한다. 복제한 문단이 원본의 좌표를 물고 있으면 자간·줄간격이 무너지는데, 본문 스타일이 전부 `JUSTIFY`(양쪽맞춤)라서 한글이 "이 줄은 몇 번째 글자까지"라는 정보대로 글자를 줄 폭에 늘려 채우기 때문이다. 원본 문장 기준 좌표를 새 문장에 적용하면 모자란 폭만큼 자간이 벌어진다.

기본 전략은 `--linesegs estimate`(줄마다 세그먼트 1개)다. `single`(문단당 1개)도 있지만 **한글에서 실제로 비교해 보고 estimate가 맞는 것으로 확인했다.** 추론만으로 이 기본값을 바꾸지 말 것 — 렌더링 결과를 보고 정한 값이다.

### 박스 슬롯 수 제약

개요·결과요약·시사점 세 블록은 1×1 테두리 박스이고, 줄 수가 원본에 고정돼 있다. plan이 더 적게 주면 남는 빈 문단은 자동 삭제되고, 더 많이 주면 초과분이 마지막 줄에 합쳐진다(경고가 출력됨). 경고가 나오면 줄 수를 줄이거나 내용을 본문으로 옮길 것.

## 생성 후 검증 — 건너뛰지 말 것

생성기는 조용히 실패할 수 있다. 파일이 열리는 것만으로는 확인이 안 된다.

```bash
python "<SKILL_DIR>/tools/verify.py" 보도자료.hwpx
```

`verify.py` 는 구조 요약, 표 정합성, ZIP 불변식을 한 번에 확인하고 문제가 있으면 0이 아닌 코드로 끝난다.

세 가지를 본다.

1. **표 오류 0** — `rowCnt` 불일치가 있으면 한글이 파일 열기를 거부한다.
2. **표 개수** — 박스 3개 + 데이터 표 N개와 맞는가. 표를 넣었는데 수가 모자라면 생성이 조용히 실패했다.
3. **원본 문장 잔여** — `python "<HWPX_SKILL>/scripts/inspect_template.py" 보도자료.hwpx` 로 텍스트를 훑어, 참고 문서(공기업 NCS 분석)의 문장이 남아 있지 않은지 확인한다. 남아 있으면 plan에 해당 블록이 누락된 것이다.

## 발행정보와 문의처

```
 2026. 8.  .
 재단법인 교육의봄
 공동대표 송인수 윤지희

문의: 안상진 부대표, 심현준 연구사업팀장 (02-6338-0660)
```

- **기관정보 푸터(웹사이트·주소·이메일)는 넣지 않는다.** 지침 문서는 푸터를 요구하지만 실제 발행본에는 없고, 지침 스스로 대표 이메일을 '미확정'으로 남겨 두었다. 확인되지 않은 연락처를 언론에 배포되는 문서에 넣는 것은 위험하다.
- **공동 발행·주최면** 참여 기관을 발행정보와 문의처에 모두 병기하고, 기관별 담당자·연락처를 나란히 적는다. 예: `교육의봄 부대표 안상진(02-6338-0660) / 사교육걱정없는세상 공동대표 신소영(02-797-4044)`
- 담당자·직책이 확실하지 않으면 추측하지 말고 물어볼 것.

## 첨부자료

보도자료 본문 말미에 첨부를 `※`로 안내하고, **HWPX와 PDF를 함께** 적는다.

```
※ 첨부자료: 「공공기관 NCS 블라인드채용 종합보고서」(HWPX) / 동 보고서(PDF)
```

첨부 보고서 자체를 만들어야 하면 **hwpx 스킬**을 쓴다. 이 스킬은 보도자료 본문 전용이다.

## 메일 제목

생성되는 HWPX 안에도 첫 줄로 들어가지만, 메일 제목은 별도로 사용자에게 텍스트로 전달할 것 — 실제 발송 시 메일 제목란에 복사해야 한다.

유형별 형식은 각 유형 레퍼런스에 있다. 공통 규칙은 `[★태그]`로 시작하고, 핵심 수치나 핵심 메시지를 제목 안에 넣고, 필요하면 끝에 `(+분석 내용 및 보고서)` 처럼 부가 자료를 병기하는 것이다.

## 톤

중립적 사실 진술과 기관 해석·제언의 2층 구조를 지킨다. 수치는 객관적으로 적고, 해석과 제언에서만 기관 입장을 명확히 낸다. 정책 비판으로 끝내지 말고 **방향 제언**으로 마무리한다 — 교육의봄 보도자료의 클로징은 늘 "채용의 변화가 교육의 변화로 이어지는" 식의 연결 메시지로 닫힌다.

협력 기관·연구자·인용 출처는 반드시 명시한다. C형(이슈 심층)은 본문 말미에 인용한 언론·정부 자료 출처 목록을 별도로 넣어 신뢰도를 확보한다.

이 문서와 `references/type-*.md` 의 규칙은 기관의 내부 작성 지침과 **실제 발행본**을 대조해 정리한 것이다. 둘이 어긋나는 지점에서는 발행본을 따랐다 — 결과 블록 기호가 지침의 `□` 가 아니라 `■` 인 것, 지침이 요구하는 기관정보 푸터를 넣지 않는 것이 그 예다.

내부 지침 원본은 배포본에 포함하지 않는다. 대조 결과가 이미 이 문서들에 반영돼 있고, 원본에는 미확정 항목(대표 이메일 등)이 남아 있기 때문이다.
